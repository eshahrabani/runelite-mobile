# Tools

**Audience:** developer
**Read this when:** you are regenerating the JDK stubs, changing a constant-pool scanner, or resolving a failed host-link gate
**Verified against:** `tools/gen_stubs.py`, `tools/RefScan.java`, `tools/JdkInfo.java`, `tools/HostLinkCheck.java`, `android/hostlink-ignore.txt`, `android/hostlink-platform-extra.txt`, `android/build.gradle` (`verifyHostLinks`)

The port ships four checked-in tools under `tools/` and two checked-in link lists under
`android/`. The tools fall into two groups: a generator that produces the `java.desktop`
stubs in `core/` (`gen_stubs.py`, driven by two Java helpers), and a gate that proves the
compiled client resolves against those stubs (`HostLinkCheck.java`). Read
[core-stubs.md](core-stubs.md) for what the stubs themselves promise; this page covers how
they are produced and checked. The two lists are reproduced in full below.

## `tools/gen_stubs.py`

Generates the data-only JDK stubs under `core/src/main/java`. The Android runtime has no
`java.desktop`, so the pre-compiled RuneLite client cannot link against the real
`java.awt`/`javax.swing`/`javax.management` classes; this script writes the subset of them
the client actually references. The member set is taken from the real call sites rather
than from a JDK API dump, so every emitted descriptor is exactly the one the client
bytecode asks for.

### CLI flags

| Flag | Default | Meaning |
|---|---|---|
| `--rl-jars` | `android/build/rl-jars` | Directory of downloaded RuneLite jars to scan |
| `--asm-cp` | required | Classpath holding `asm`/`asm-tree` for the helper tools |
| `--out` | `core/src/main/java` | Stub source root |
| `--work` | `build/stubgen` | Scratch dir (`members.txt`, `jdkinfo.txt`, `query.txt`, `need.txt`, compiled helpers) |
| `--repo` | `.` | Repo root |

There is no `--only` flag here; `--only`/`--withsource` exist only inside `RefScan.java` and
are never passed by the generator.

### Marker header and the refusal rule

Generated files carry the javadoc marker `Data-only stub for {@code <FQCN>}` and the line
`Generated by tools/gen_stubs.py -- do not hand-edit.` (`gen_file`). Origin is decided by
content, not by path: walking `core/src/main/java` **and** `hostshims/src`, a file is
treated as hand-written iff `MARKER = "Data-only stub for {@code"` is absent from its first
4096 bytes.

The rule has two teeth:

- A target file that already exists and lacks the marker in its first 4096 bytes is skipped,
  never overwritten (target-write loop).
- Stale cleanup deletes a file only if the marker is present in its first 4096 bytes
  (stale-removal loop). A hand-written file can therefore never be removed by the generator.

Never hand-edit a file that carries the marker: the next run rewrites it in full. Hand-edited
exceptions belong in the hand-written sets described in [core-stubs.md](core-stubs.md).

### How the member set is derived

1. `compile_helpers()` javac-compiles `RefScan.java` and `JdkInfo.java` into `<work>/tools`.
2. `scan_members()` lists `--rl-jars`, excludes names ending `-runtime.jar`, and runs
   `RefScan members` over the remaining jars, writing `members.txt`. The **downloaded** jars
   are scanned, not the cleaned ones: the host shims replace a handful of classes the build
   strips (`ui/laf/**`, plus `ClientUI`, `SplashScreen`, `FatalErrorDialog`,
   `ContainableFrame`, `OSXFullScreenAdapter`, `PluginHubPanel`), so those classes'
   references to `java.desktop` types are exactly the stub surface the shims need.
3. `RefScan` emits per class `DECL\t<class>\tM name desc` / `F name desc`, `HIER\t<class>\tsuper\tifaces`,
   and reference lines `M owner.name <flag>desc`, `F owner.name <flag>desc`, `C owner`.
4. `load_members()`/`load_declared()`/`load_hierarchy()` parse those lines.
5. Inheritance attribution: a member called through a client-jar subtype whose declaration
   lives in a JDK ancestor is re-attributed to the nearest non-scanned ancestor
   (`first_jdk_ancestor`), after skipping replaced classes (`replaced_class`) and members
   whose signature mentions a client-jar type. Without this, a stub would never declare the
   member and ART would throw `NoSuchMethodError` on device.
6. A transitive type closure runs, with six fixed-point passes that re-query `JdkInfo` until
   the `need` set stops growing.

### Staticness is decided by the call site, not the JDK

`RefScan.flag(opcode, staticOpcode)` returns `S` for the static opcode and `-` otherwise;
fields test `GETSTATIC`/`PUTSTATIC`. `gen_stubs.emit_members` reads the leading flag char
(`desc.startswith("S")`) to emit `public static` versus instance members. The reason is
recorded in the source: wrong staticness is an ART `IncompatibleClassChangeError` at link
time.

### Hierarchy, constants and enums come from the local JDK

`JdkInfo` is run on `query.txt` and emits `TYPE`, `FIELD`, `ENUM`, `ABSTRACT`, `CTOR`,
`MISSING` lines, which `load_jdkinfo()` parses. Emission uses:

- kind, supertype, interfaces and enclosing class from `TYPE` (`decl`/`extends_clause`);
- constants: the real JDK field value when readable, else the primitive default;
- enums: the JDK constant names spliced at the top of the body;
- abstract methods: a stub with no referenced constructor is marked abstract (an abstract
  class satisfies the inherited JDK abstract methods) and only `clone()` is emitted;
  otherwise inherited methods get concrete bodies.

This is what lets ART's verifier see the same type relationships the real JDK classes have.

### Invocation

It is a **manual** step. The docstring claims it is "also wired as the `:android:generateJdkStubs`
Gradle task", but no such task exists: a repo-wide grep of `*.gradle` for
`gen_stubs`/`generateJdkStubs` returns zero hits. Run it directly, pointing `--asm-cp` at the
ASM jars the build resolves (the buildscript pins `asm`/`asm-commons` 9.6):

```bash
python3 tools/gen_stubs.py --rl-jars android/build/rl-jars \
  --asm-cp "$(find ~/.gradle/caches -name 'asm-9.6.jar' | head -1):$(find ~/.gradle/caches -name 'asm-tree-9.6.jar' | head -1)" \
  --out core/src/main/java --work build/stubgen
```

Run it after a RuneLite client bump, then rebuild and run `:android:verifyHostLinks`. The
generator's `SCAN_PREFIXES` and `HAND_PREFIX` constants are referenced only by their own
definitions, so treat them as inert documentation.

## `tools/RefScan.java`

An ASM constant-pool scanner over jars or directories of `.class` files. Three modes:

| Mode | Invocation | Output |
|---|---|---|
| `refs` | `RefScan refs <jar...>` | Referenced owners, one `owner count` line each (the count is how many reference kinds — method, field, class — mention the owner) |
| `members` | `RefScan members <jar...>` | `M`/`F`/`C` reference lines plus per-class `DECL`/`HIER` lines |
| `api` | `RefScan api <provided...> --use <jar...>` | Per `--use` reference, members missing from the indexed set (supertype-walking via `missingMember`) |

Options are `--only <prefix,...>` (owner filter) and `--withsource` (append `<- <class>`);
`selected()` (and `refs`' own `only` check) is a no-op when `only` is empty.

Only `members` has an in-repo caller: `gen_stubs.scan_members()`. `refs` and `api` are
tools-only. The scan reads `MethodInsnNode`, `FieldInsnNode`, `TypeInsnNode`,
`MultiANewArray`, `Ldc` (Type/Handle/`ConstantDynamic`) and `InvokeDynamicInsnNode`, plus
generic signatures via `refSig`, and emits the `DECL`/`HIER` lines unconditionally.

## `tools/JdkInfo.java`

Dumps the local JDK's real shape for a list of internal names read from a file argument. It
is invoked only by `gen_stubs` on `<work>/query.txt`. Tab-separated line kinds:

| Kind | Fields |
|---|---|
| `TYPE` | Internal name, kind (annotation/`enum`/`interface`/`class`), abstract, final, static, super, interfaces, enclosing |
| `FIELD` | Owner, name, type, static, final, constant value or `-` |
| `ENUM` | Owner, constant name |
| `ABSTRACT` | Owner, method name, descriptor (a public/protected abstract method not concretely implemented in the hierarchy) |
| `CTOR` | Owner, constructor descriptor (non-private) |
| `MISSING` | Internal name (the class could not be loaded from the local JDK) |

## `tools/HostLinkCheck.java`

Verifies that every JDK-platform member the pre-compiled client jar and the app's own classes
reference actually exists in what this repo provides, turning on-device
`NoClassDefFoundError`/`NoSuchMethodError` hazards into a build-time list.

### Invocation and classpath

Run it through the Gradle task:

```bash
./gradlew :android:verifyHostLinks
```

`verifyHostLinks` depends on `downloadAndDexJar`, `:core:compileJava` and
`compileReleaseJavaWithJavac` (see the `verifyHostLinks` task in `android/build.gradle`). It
is **deliberately not** wired into `assembleRelease`: it depends on the release javac output
and would otherwise block device builds while a stub is being written.

The task compiles the tool with the buildscript ASM classpath
(`buildscript.configurations.classpath` entries whose name starts with `asm`) and runs:

```text
java -cp <toolOut>:<asmCp> HostLinkCheck --provided <...> --use <...> \
  --ignore-list android/hostlink-ignore.txt --platform-extra android/hostlink-platform-extra.txt
```

- `--provided`: `core/build/classes/java/main`, the Android release classes
  (`build/intermediates/javac/release/classes`), `build/host-shims/classes`,
  `platforms/android-34/android.jar`, the runtime jar libraries in `rl-jars` (excluding
  `-runtime`, `client-*`, `injected-client-*`, `runelite-api-*`), and the three **cleaned**
  jars `client-cleaned.jar`, `injected-client-cleaned.jar`, `runelite-api-cleaned.jar`.
- `--use`: the three cleaned jars plus the Android release classes, shim classes and core
  classes. `core/` is checked as well as provided because its own stubs call each other, and
  the API jar is checked so the full API surface is covered.

Optional flags on the tool itself: `--prefix p1,p2,...` (owner filter), `--ignore <substring>`
(repeatable), `--ignore-list <file>`, `--platform-extra <file>`.

### Resolution algorithm

`resolve()`:

1. Parse the `M`/`F` flag, name and descriptor. A method flag is `S` (INVOKESTATIC),
   `I` (INVOKEINTERFACE), `E` (INVOKESPECIAL) or `-` (INVOKEVIRTUAL).
2. If a virtual call (`-`) has an **interface** constant-pool owner, report
   `virtual call on interface owner` — that is an `IncompatibleClassChangeError` on device
   (JVMS 5.4.3.3).
3. `findDeclaring` walks the owner and its supertypes for a name+descriptor match, setting
   `reachedPlatform` when a `java.*` type outside the provided set is met.
4. If nothing is found and the reference is a method, retry with the d8 covariant descriptor.
5. If found, check the call-site shape (`shapeMismatch`).
6. If `reachedPlatform`, the Android platform supplies it: OK.
7. Otherwise report `class missing:`, `method missing:` or `field missing:`.

### Modelled rules

- **d8 covariant `java.nio.Buffer` returns** (`d8CovariantDesc`): when the owner starts
  `java/nio/` and ends `Buffer`, the method is one of `position`, `limit`, `mark`, `reset`,
  `clear`, `flip`, `rewind`, and the descriptor returns the owner itself, it is rewritten to
  return `Ljava/nio/Buffer;`. d8 rewrites the OpenJDK-9+ covariant returns to the platform
  signature (verified against the shipped dex), so the jar's descriptor is not a gap.
- **Array-typed constant-pool owners** (`addOwner`): an owner may be an array descriptor
  (`ANEWARRAY`'s operand, and the `"array".clone()` `Methodref` javac emits for every enum's
  `values()`). It is mapped to the element class, since the array type's only member is
  `clone()`.
- **Signature-polymorphic members skipped** (`membersOf`): the whole
  `java/lang/invoke/VarHandle` owner is skipped, and `MethodHandle.invoke`/`invokeExact` are
  skipped — their constant-pool descriptor describes the call site, never the declared
  member, and `transformClassBytes` emits such a call.
- **JVMS 5.4.3.3/5.4.3.4 call-site shapes** (`shapeMismatch`): `S` (INVOKESTATIC) requires a
  static member and is legal on an interface owner; `I` (INVOKEINTERFACE) requires the
  declaring class to be an interface, except for the public `java.lang.Object` methods every
  interface implicitly declares (JVMS 9.2, e.g. `Editable.toString()`); `-`/`E` require a
  non-static member, and resolving to a superinterface method from a class owner is legal.

### Ignore list versus platform-extra

- `--ignore-list` prefixes are matched against **either** the referenced owner (a library the
  port never loads) **or** the referencing class (a desktop-only consumer the port never
  runs), and a referencing-class match skips the whole class.
- `--platform-extra` is deliberately **not** an ignore list: the same owner's other
  references are still reported, a matched entry is recorded so it cannot mask a future
  regression, and any entry that matches nothing prints
  `# warn: platform-extra entry matched nothing:`.

### Output and exit code

Lines are sorted as `"<referencing.class>: <problem>"`, followed by a summary line
`# missing: N (provided classes: X, checked classes: Y)` and `# missing classes: Z`. Any
missing entry makes the process `System.exit(1)`. A gap line names the **referencing** class,
not the missing owner: a gap is only actionable when you know which plugin or stub drags it
in.

## The checked-in link lists

`android/hostlink-ignore.txt` has 10 active entries. The header states a prefix may match the
referenced owner or the referencing class:

| Prefix | Stated reason |
|---|---|
| `org/lwjgl/` | GPU/lwjgl consumers; `GpuPlugin` is excluded |
| `com/sun/jna/` | native/JNA consumers; `WorldHopperPlugin` is excluded |
| `net/runelite/discord/` | `DiscordPlugin` is excluded |
| `net/runelite/rlawt/` | desktop AWT shell |
| `ch/qos/logback/` | slf4j-simple replaces logback on this port |
| `com/formdev/flatlaf/` | host replaces the Swing laf; `laf/` is stripped |
| `net/runelite/jshell/` | `DevToolsPlugin` is excluded |
| `net/runelite/client/plugins/worldhopper/ping/` | JNA ping helper of an excluded plugin |
| `net/runelite/client/Updater` | desktop self-updater; `ClientUpdater.java` replaces it (never executed) |
| `java/beans/` | libcore supplies `java.beans` (probe-verified on device); `core/`'s copies exist only because `javac --limit-modules` hides `java.desktop`, and the boot classpath shadows them at runtime |

`android/hostlink-platform-extra.txt` has 5 active entries: references the shipped runtime
resolves but `android.jar` does not model, each verified by a reflection probe on the device
(compile a probe class with `javac --release 11`, dex it with `d8 --min-api 26`, run it with
`adb shell dalvikvm -cp /data/local/tmp/probe.dex Probe` on a Pixel 8 Pro, API 34). Member
entries are `owner.name desc`; a bare `owner` is the class-presence form:

| Entry | Kind |
|---|---|
| `java/lang/ClassLoader.getPlatformClassLoader ()Ljava/lang/ClassLoader;` | member |
| `java/nio/file/Files.readString (Ljava/nio/file/Path;)Ljava/lang/String;` | member |
| `java/nio/file/Files.writeString (Ljava/nio/file/Path;Ljava/lang/CharSequence;Ljava/nio/charset/Charset;[Ljava/nio/file/OpenOption;)Ljava/nio/file/Path;` | member |
| `java/util/concurrent/ConcurrentHashMap.keySet ()Ljava/util/concurrent/ConcurrentHashMap$KeySetView;` | member |
| `sun/misc/Unsafe` | class |

The third list, `android/plugin-exclusions.txt`, is a plugin-index input rather than a link
gate input; it is documented in [build-and-release.md](build-and-release.md). A gap *inside*
a plugin that stays in the index is never fixed by either list — fix the stub or exclude the
plugin there.
