# Swing sidebar + weekly-build CI fix

## Context

Two asks.

1. **Full desktop sidebar.** Today the port strips RuneLite's Swing shell (`android/build.gradle` `HOST_REPLACED_CLASSES`/`HOST_REPLACED_PREFIXES`), replaces 23 classes under `net/runelite/client/ui/**` with data-only shims, and lists plugin panels in the native drawer as `"registered panels (Swing, not available on mobile)"`. Eleven plugins are excluded from the plugin index *only* because their `PluginPanel` cannot be constructed (`android/plugin-exclusions.txt`). Goal: run RuneLite's **unmodified** `ClientToolbarPanel`, `NavigationButton`, `PluginPanel`, `MultiplexingPluginPanel`, `DynamicGridLayout`, `ui/components/**` (IconTextField, MaterialTabGroup, ColorJButton, colorpicker, …) and every plugin panel on top of a hand-written Swing/AWT runtime in `core/`, rendered into a bitmap that the Android drawer presents. Plugin panels must be interactive: mouse/keyboard events, scrolling, popups, dialogs, text entry.
2. **Green weekly build.** `Build Android Client` fails at `android-actions/setup-android@v3`: the action downloads cmdline-tools 16.0 whose `sdkmanager` requires JDK 17+, but the job sets up Zulu 11 (`This tool requires JDK 17 or later. Your version was detected as 11.0.32.` → exit 1). `Compile iOS Client` fails at `xcode-select -s /Applications/Xcode_15.0.1.app/Contents/Developer` (`invalid developer directory`; `macos-latest` no longer has that Xcode).

End state: `./gradlew :android:assembleRelease` ships a client whose drawer is RuneLite's own Swing sidebar (icon strip + real panels, including the real Configuration panel), every panel-bearing plugin enabled, host diagnostics moved to the launcher screen, and the weekly workflow green.

## Decisions already made (do not re-litigate)

- Drawer body = the Swing sidebar **only**. The native `Plugins`/`Config`/`Host` tabs, the plugin search field, the plugin rows, the config form and the host rows are deleted. Host diagnostics (runtime status, client version, index size, active plugins, load failures, client-AOT row, conformance button + summary) move to the **launcher screen**.
- Scale: the sidebar **fills the drawer** at an **integer** UI scale. 272 is the sidebar's logical preferred width (plugin panel 242 + tab strip ≈30); `uiScale = clamp(floor(contentWidthPx / 272), 1, 3)`, `logicalWidth = round(contentWidthPx / uiScale)`, `logicalHeight = round(contentHeightPx / uiScale)`, where `contentWidthPx`/`contentHeightPx` are the drawer's inner pixel size. At `logicalWidth > 272` the panels stretch (viewport rule below). **Rasterisation is at device resolution**: the stage root is bounded in logical units and painted through a `Graphics` scaled by `uiScale`, so glyphs are rasterised at `fontSize × uiScale` device pixels and the app presents the bitmap 1:1 (no upscale blur).
- Plugin Hub: **best-effort rendering with per-plugin failure isolation**; no in-app hub installer. `PluginHubPanel` (the hub browser tab inside `TopLevelConfigPanel`) is replaced by a host shim.
- Un-exclude every panel plugin: Config, LootTracker, Notes, TimeTracking, SkillCalculator, ScreenMarker, WorldHopper, Hiscore, GrandExchange, KourendLibrary, Info. Keep excluded: `GpuPlugin` (LWJGL), `DiscordPlugin` (JNA), `WorldMapPlugin` (LWJGL/worldmap), `DevToolsPlugin` (FlatLaf + runelite-jshell + logback), `ScreenshotPlugin` (desktop screenshot folder).
- Threading: introduce a **dedicated Swing event-dispatch thread** (see B0); the Android main thread only renders bitmaps and delivers input.

## Approach

### Phase A — CI fixes (independent of everything below; do first)

**A1. Android job JDK.**
Edit `.github/workflows/build.yml`, job `build-android`, step `Set up JDK 11` → `Set up JDK 17` (`distribution: 'zulu'`, `java-version: '17'`, `cache: 'gradle'` unchanged). Two independent reasons: (a) `android-actions/setup-android@v3` installs cmdline-tools 16.0, whose `sdkmanager` requires JDK 17+ (`This tool requires JDK 17 or later. Your version was detected as 11.0.32.`); (b) the build itself cannot run on 11 — root `build.gradle` pins `com.android.tools.build:gradle:8.2.2` with the Gradle 8.5 wrapper, and AGP 8.x requires JDK 17. No other android-job change: `android/build.gradle` pins `sourceCompatibility`/`targetCompatibility` 11 (bytecode stays Java 11), and JDK 17's javac still honours `--limit-modules java.base,jdk.unsupported` (`core/build.gradle`), which is what makes the `java.awt.*`/`javax.swing.*` packages compilable.
Check: `grep -n "java-version" .github/workflows/build.yml` shows `'17'` for `build-android` and `'11'` for `build-ios`; then a manual `workflow_dispatch` run of the workflow reaches "Build Android APK" and publishes the release.

**A2. iOS Xcode selection.**
Replace the `Set up Xcode` step's body with a version-agnostic pick plus a print:
```bash
XCODE_APP="$(ls -d /Applications/Xcode*.app | sort -V | tail -n1)"
sudo xcode-select -s "$XCODE_APP/Contents/Developer"
xcodebuild -version
```
(no third-party action; `latest-stable` Xcode is whatever the runner image ships). Keep the job on JDK 11 (RoboVM 2.3.24).
**A3. iOS job must not gate the weekly release.**
Add `continue-on-error: true` to the `build-ios` job (sibling of `runs-on`) with the comment `# Skeleton target: a Toolchain/Xcode incompatibility must not turn the weekly client build red; the IPA stays a workflow artifact.` `distribute` already `needs: [build-android]`.
Check: `grep -n "continue-on-error" .github/workflows/build.yml` → 1 hit under `build-ios`; a dispatch run shows `build-android` success and `build-ios` non-blocking.

### Phase B — core Swing runtime (`core/src/main/java/{java,javax}/**`)

Rules for this phase, all load-bearing:
- Hand-written files are never regenerated (marker rule in `docs/core-stubs.md` §2). Implement behavior **by hand** in the listed files; when a member is missing entirely, add it by hand too. **Converting a generated stub into a hand-written implementation means rewriting the file so that the string `Data-only stub for {@code` no longer appears in its first 4096 bytes** (that is the only discriminator the generator uses) — from then on `tools/gen_stubs.py` skips it, so the B work survives C3's regeneration.
- Only after phase C changes the strip lists, re-run `tools/gen_stubs.py` (C3) to add any *remaining* data-only members, then re-hand-implement anything on the behavior list below that the run turned back into a stub.
- JDK semantics are the contract unless stated otherwise. Where the JDK behavior is unspecified (exact pixel of an antialiased edge, tooltip timing), the port's choice is stated.
- Every step's gate is `./gradlew :core:compileJava` (offline) plus the self-tests added in B8 at the points named there. No step may leave a `null`-returning member on the *behavior list*.

**B0. Threading model + bridge (do before B1, it is what B3 relies on).**
- `core/src/main/java/org/runelite/mobile/bridge/AWTBridge.java`: `registerUiThread(Thread, Executor)` becomes "register the **Swing EDT**". Add `static Thread swingThread()`, keep `isUiThread()` = `Thread.currentThread() == swingThread`, keep `post(Runnable)` (enqueue on the Swing queue) and `invokeAndWait(Runnable)` (blocks caller, rethrows as `RuntimeException`; if already on the Swing thread run inline).
- New `core/src/main/java/org/runelite/mobile/bridge/SwingEdt.java`: owns one daemon thread named `Swing-EDT-rlmobile` (priority `NORM`), a `LinkedBlockingDeque<Runnable>` event queue, `post/invokeAndWait/isDispatchThread/dispatchQueued`. Started lazily on first `post`/`invokeAndWait` by `SwingEdt.ensureStarted()`; `MainActivity.onCreate` calls `AWTBridge.registerUiThread(SwingEdt.ensureStarted(), r -> SwingEdt.post(r))` **after** creating it via `SwingEdt.ensureStarted()`.
- New `core/src/main/java/org/runelite/mobile/bridge/UiBridge.java` (core ↔ app contract; all methods callable from either thread unless marked):
```java
public final class UiBridge {
  public interface Host {                       // implemented in the app dex
    void sidebarDirty();                        // Swing thread
    void windowDirty();                         // Swing thread
    void textInputRequested(boolean show);      // Swing thread
    void toast(String message);                 // Swing thread; message may be a tooltip or an unsupported-feature notice
    void closeSidebarRequested();               // Swing thread: RuneLite's own sidebar toggle was clicked
  }
  static volatile Host host;
  public static void setHost(Host h);
  public static void setScreenSize(int w, int h, float density);
  public static void setSidebarRoot(javax.swing.JComponent root);     // asset dex (ClientUI shim)
  public static boolean hasSidebar();
  public static void setSidebarBounds(int logicalW, int logicalH, float scale); // app: stage geometry in logical units, validates + repaints
  public static float sidebarScale();
  public static void paintSidebar(int[] argb, int deviceW, int deviceH); // Swing thread only; argb is device-sized, the paint applies `scale`
  public static int[] windowLogicalSize();                            // {w,h} of the top-most visible window, or null
  public static void paintWindow(int[] argb, int deviceW, int deviceH); // Swing thread only; zero-fills when no window
  public static boolean hasVisibleWindow();
  public static void dispatchMouse(int x, int y, int id, int button, int clickCount, int modifiers, long when); // app → Swing thread
  public static void dispatchWheel(int x, int y, int wheelRotation, int clickCount, int modifiers, long when);
  public static void dispatchKey(int id, int keyCode, char keyChar, int modifiers, long when);
  public static void setSidebarVisible(boolean visible);              // app: activates/deactivates the selected panel
  public static String tooltipAt(int logicalX, int logicalY);
  public static boolean focusOwnerIsTextInput();
  public static void notifyUnsupported(String feature);               // logs once per feature + host.toast("not supported on mobile: " + feature)
}
```
  `dispatchMouse/Wheel/Key` construct the AWT event with the correctly hit-tested source component/popup and dispatch it on the Swing thread (they internally `SwingEdt.post` if the caller is not the Swing thread).
- Marshalling cutover (must all be done in this step so nothing later calls Swing off-thread): `RuneLiteHost.start` / `startPlugins` (already posts via `AWTBridge.post` → now the Swing thread), `RuneLiteHost.flushConfig`, `setPluginEnabled`, `setPluginEnabledFlag`, `startPlugin`/`stopPlugin`, `pluginConfigClass`, `plugins()`, `isPluginEnabled`, `indexSize`, `clientVersion` (reflection reads stay plain reads, but any write/start/stop wraps in `AWTBridge.invokeAndWait` when `!AWTBridge.isUiThread()`), `MainActivity.onStop`'s flush, `SidePanel`'s calls into `RuneLiteHost`, `PluginConformance.run`.
- Check (B8 case `threading`): from the Android main thread, `AWTBridge.post` runs on a thread whose name is `Swing-EDT-rlmobile`; `SwingUtilities.isEventDispatchThread()` is true only there; `PluginManager.startPlugins` succeeds unchanged.

### Phase D — Android presentation

**D1. `SwingSidebarView`** (new, `android/src/main/java/org/runelite/mobile/SwingSidebarView.java`): a `View` in the drawer body.
- Owns `Bitmap stage` (`ARGB_8888`, `setHasAlpha(true)`), an `int[] pixels` and a `Paint`; on size change computes `uiScale = clamp(floor(contentWidthPx / 272), 1, 3)`, `logicalW = round(contentWidthPx / uiScale)`, `logicalH = round(contentHeightPx / uiScale)`, allocates `pixels = new int[contentWidthPx * contentHeightPx]` and calls `AWTBridge.invokeAndWait(() -> UiBridge.setSidebarBounds(logicalW, logicalH, uiScale))`.
- `onDraw` blits `stage` into the view rect 1:1 (`canvas.drawBitmap(bitmap, src, dst, paint)`, `src == dst ==` the view bounds, `setFilterBitmap(false)`); if `!UiBridge.hasSidebar()` it draws nothing and the drawer shows the runtime-status `TextView` placeholder underneath (text `"RuneLite runtime not running: <status>"`).
- Implements `UiBridge.Host`: `sidebarDirty()` → post a `render()` request to the Android main thread, coalesced (at most one pending render; renders at most every 16 ms); `render()` = `AWTBridge.invokeAndWait(() -> UiBridge.paintSidebar(pixels, contentWidthPx, contentHeightPx))` then `bitmap.setPixels(pixels, 0, contentWidthPx, 0, 0, contentWidthPx, contentHeightPx)` + `invalidate()`; `windowDirty()` → same for the window layer (D3); `textInputRequested(show)` → callback to `MainActivity` (show/hide the keyboard bar); `toast(msg)` → Android `Toast`; `closeSidebarRequested()` → `sidePanel.close()`.
- Touch → Swing: `ACTION_DOWN` = `MOUSE_MOVED` (hover) + `MOUSE_PRESSED` (BUTTON1) at the logical point + arm a 400 ms long-press timer (cancelled by movement > 10 dp); `ACTION_MOVE` = `MOUSE_DRAGGED`; `ACTION_UP` = `MOUSE_RELEASED` + `MOUSE_CLICKED` (clickCount 1); cancel/leave → `MOUSE_RELEASED`. Long press: `MOUSE_PRESSED`/`MOUSE_RELEASED` with BUTTON3 at the same point (popup trigger) and, if `UiBridge.tooltipAt(x,y)` is non-null, `Toast` the tooltip.
- Two-finger gesture: track `ACTION_POINTER_DOWN`; a vertical centroid move dispatches `MOUSE_WHEEL` events (`wheelRotation = -delta / 8`, at least 1 per 24 dp) to the point under the first finger; a two-finger tap maps to BUTTON3 press/release (same as the game's two-finger tap = right click).
- Key routing: `dispatchKeyText(String)`/`dispatchKeyCode(int)` are called by `MainActivity` when `UiBridge.focusOwnerIsTextInput()`; they build `KeyEvent`s (KEY_PRESSED + KEY_TYPED + KEY_RELEASED) and call `UiBridge.dispatchKey(...)`. When the focus owner is not a text component, the events go to the game exactly as today.
- Scroll fling: none (documented); `JScrollBar` thumb drag works.

## Assumptions & contingencies

- **Dedicated Swing EDT.** Assumed safe because every plugin-visible contract goes through `SwingUtilities`/`AWTBridge`, and the client's own rendering stays on the client thread. If a device check shows plugin lifecycle regressions (a plugin that no longer starts, a `PluginManager` EDT assertion failing), the fallback is to make `AWTBridge.registerUiThread` register *both* threads (Android main thread kept as an accepted EDT for lifecycle entry points, the Swing thread used for Swing) — at the cost of `JOptionPane` modality being non-blocking.
- **Verification needs a device.** No JUnit exists and the `java.*`/`javax.swing.*` classes shadow the desktop JDK, so they cannot run on a host JVM: B8's self-tests and the panel conformance are device-run. Offline, the only gates are `:core:compileJava` and code review.
- **Generator output is JDK-dependent.** `tools/gen_stubs.py`/`tools/JdkInfo.java` model hierarchy/constants/enums from the running JDK, so the stub set produced under JDK 17 differs in members from one produced under 11. Run the regeneration with JDK 17 (the same JDK as local builds) and treat `:android:verifyHostLinks` + B8 as the gates.
- **`JTable`/`JTree`** are implemented only to the depth in B5. DevTools stays excluded; a hub plugin needing editing/sorting in those widgets renders but its edit gestures may not work (reported as a panel error or silent no-op, never a crash).
- **`WorldHopperPlugin`** needs JNA for ping: the panel and world list work, ping values stay blank; if `startUp` throws on the device, restore its exclusion line and note the reason in `android/plugin-exclusions.txt`.
- **`InfoPlugin`** depends on B6's `JEditorPane`; if link hit-testing cannot be finished, restore its exclusion line with the reason `JEditorPane HTML/link rendering`.
- **FlatLaf stays out.** If `:android:verifyHostLinks` reports a missing `com/formdev/flatlaf/**` member, add exactly that member as a constants/no-op class in `core/` (never ship the FlatLaf jar).
- **Fractional scale** is intentionally not used: the integer scale keeps 1 px borders uniform with the hard-edged rasterizer. If a device shows the sidebar too small (narrow phones end at `scale=1`), the single knob is the drawer-width policy in `SidePanel`'s constructor — widening it raises the integer scale.
